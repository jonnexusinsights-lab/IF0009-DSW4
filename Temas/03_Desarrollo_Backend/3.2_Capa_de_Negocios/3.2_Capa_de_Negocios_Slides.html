¿Qué es la Capa de Negocios?

  • Núcleo Lógico del Sistema:
    • Representa el lugar donde residen las reglas, políticas y flujos del negocio.
    • Independiente del canal de entrega (ej. API REST, interfaz gráfica, cola de mensajería).
  • Responsabilidades Clave:
    • Validar reglas de dominio complejas (ej. verificar cupos o saldos).
    • Coordinar llamadas entre múltiples repositorios.
    • Controlar la consistencia mediante límites transaccionales.
    • Declarada mediante la anotación estereotipo @Service en Spring Boot.

Inyección de Dependencias: Campo vs Constructor

  • Inyección por Campos (Mala Práctica):
    • Uso de @Autowired directo en los atributos privados.
    • Dificulta pruebas unitarias porque requiere levantar el contexto de Spring.
  • Inyección por Constructor (Buena Práctica - Estándar):
    • Declarar los atributos como finales (final) y proveer un constructor.
    • Inmutabilidad: Garantiza que no cambien tras instanciar.
    • Fácil de testear: Permite pasar mocks usando new en pruebas unitarias.
    • Luz de alerta: Si hay más de 5 parámetros, indica baja cohesión.

Transacciones y la Anotación @Transactional

  • Transacción: Conjunto de operaciones en BD ejecutadas como unidad única.
    • Debe cumplir las propiedades ACID.
  • Gestión en Spring Boot:
    • Anotación @Transactional para manejar de forma declarativa.
  • Parámetros Esenciales:
    • propagation: Cómo se unen o separan las transacciones en llamadas.
    • isolation: Visibilidad de cambios concurrentes (evita lecturas sucias).
    • rollbackFor: Especificar ante qué excepciones deshacer cambios.
    • readOnly: Optimización para consultas puras.

Propagación y Aislamiento Transaccional

  • Niveles de Propagación:
    • REQUIRED (Por defecto): Se une a la existente o crea una nueva.
    • REQUIRES_NEW: Suspende la transacción actual y crea una nueva separada.
    • MANDATORY: Exige que exista una transacción previa.
  • Niveles de Aislamiento:
    • READ_COMMITTED: Solo lee registros ya confirmados.
    • REPEATABLE_READ: Lecturas consistentes del mismo registro.
    • SERIALIZABLE: Ejecución secuencial (máxima seguridad, menor rendimiento).

Políticas de Rollback y Optimización

  • Comportamiento ante Excepciones por Defecto:
    • Hace rollback para excepciones no marcadas (RuntimeException).
    • No hace rollback por defecto para excepciones marcadas (Exception).
  • Personalización de Rollback:
    • Usar @Transactional(rollbackFor = Exception.class) para revertir ante todo error.
  • Optimización con readOnly:
    • @Transactional(readOnly = true) desactiva el dirty checking en Hibernate.
    • Ahorra CPU y memoria en métodos de solo consulta.

Analogías del Tema

  • El Chef y la Transacción de Cocina:
    • Si la carne se quema, el Chef descarta también el puré (hace rollback) para no entregar un plato incompleto. Solo si ambos están perfectos, la orden se confirma (se hace commit).
  • Inyección por Constructor vs Campo:
    • Por constructor es un carro ensamblado con sus piezas en fábrica.
    • Por campo es como tratar de colocar el motor al carro mágicamente mientras va en marcha por la autopista.

    @Transactional(rollbackFor = MatriculaException.class)
    public Matricula matricularCurso(Integer estudianteId, Integer cursoId) {
        Estudiante estudiante = estudianteRepository.findById(estudianteId)
                .orElseThrow(() -> new MatriculaException("No existe."));

        Curso curso = cursoRepository.findById(cursoId)
                .orElseThrow(() -> new MatriculaException("No existe."));

        if (curso.getCuposDisponibles() <= 0) {
            throw new MatriculaException("Sin cupos.");
        }

        curso.disminuirCupo();
        cursoRepository.save(curso);

        Matricula matricula = new Matricula(estudiante, curso);
        return matriculaRepository.save(matricula);
    }

Trampas Comunes en Servicios

  • Auto-Invocación (Self-Invocation):
    • Invocar un método @Transactional desde otro método interno de la misma clase. Se evade el proxy de Spring y la transacción no se ejecuta.
  • Ignorar Excepciones Marcadas:
    • Creer que Spring hace rollback ante errores de lectura de archivo u otros sin configurar rollbackFor.
  • Falta de Transaccionalidad de Solo Lectura:
    • Omitir readOnly = true en búsquedas largas de registros, ralentizando el backend.

Pregunta de Reflexión

  • Si un método con @Transactional(propagation = Propagation.REQUIRED) llama a otro anotado con Propagation.REQUIRES_NEW, y el segundo método falla lanzando una excepción:
    • ¿Cómo afecta esto los cambios realizados por el método que inició la llamada?
    • ¿Cómo deberíamos capturar y procesar el error en la primera capa para evitar que toda la transacción global falle y se descarte?
