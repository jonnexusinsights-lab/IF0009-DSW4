# ¿Por qué emplear Capas en el Código?

* **Complejidad del Software:** Las aplicaciones crecen agrupando cientos de clases colaborativas.
* **Código Espagueti:** Mezclar bases de datos, validaciones y diseño visual acopla el código y lo hace frágil.
* **Separación de Incumbencias (*Separation of Concerns*):**
  * Agrupar componentes con especializaciones operativas comunes.
  * Establecer jerarquías de dependencias unidireccionales y limpias.
  * Facilitar mantenimiento, testeo en paralelo y reusabilidad.

# Arquitectura Lógica versus Física

* **Arquitectura Lógica (`N-Layer`):**
  * Segregación del código a nivel de diseño y código fuente (paquetes).
  * Ej: paquetes `.domain`, `.data`, `.business`, `.controller` en Java.
  * Facilita la legibilidad y mantenimiento del código.
* **Arquitectura Física (`N-Tier`):**
  * Distribución del software ejecutándose en distintos servidores físicos o nodos de red (tiers).
  * Clásica de 3-Tier: Cliente (Navegador) $\rightarrow$ Servidor de Aplicación (Spring Boot) $\rightarrow$ Base de Datos.

# Responsabilidades de las Capas en Spring Boot

* **Controladores (`@RestController`):** Intercepta peticiones HTTP, valida datos, gestiona respuestas y códigos HTTP.
* **Negocio / Servicios (`@Service`):** Contiene las reglas, lógica de negocio y delimita transacciones.
* **Datos / Repositorios (`@Repository`):** Realiza operaciones de lectura/escritura físicas en la base de datos (JPA).
* **Dominio / Comunes (`domain`):** Entidades y modelos de datos representativos del negocio (compartidos).

# La Pirámide de Pruebas Automatizadas

* **Desacoplar en capas facilita el testeo:**
* **Unit Tests (Pruebas Unitarias):** Evalúan métodos de clases aisladas en memoria sin contexto del framework (rápidas).
* **Integration Tests (Pruebas de Integración):** Validan la interacción real entre servicios y repositorios (cargan el contexto Spring).
* **Web/API Tests:** Prueban endpoints enviando solicitudes HTTP simuladas.

# Analogía Lógica y Física de las Capas

* **El Diseño de una Empresa (N-Layer):**
  * Departamentos especializados: Ventas (Presentación), Ingeniería (Negocios), y Compras (Datos).
  * El vendedor no calcula estructuras ni va a buscar materiales; coordina solicitudes de forma ordenada.
* **Los Edificios Físicos de la Empresa (N-Tier):**
  * Oficina comercial céntrica (Cliente), planta administrativa (Backend) y bodega industrial aislada (Base de Datos).
  * Si la bodega colapsa físicamente, los demás edificios continúan de forma aislada e independiente.

# Código: El Controlador REST (`PeliculaRestController.java`)

```java
@RestController
@RequestMapping("/api/peliculas")
public class PeliculaRestController {
    @Autowired private PeliculaService service;

    @PostMapping
    public ResponseEntity<?> registrar(
            @Validated @RequestBody PeliculaCreationDTO dto,
            BindingResult validacion) {
        if (validacion.hasErrors()) {
            return ResponseEntity.badRequest().body(validacion);
        }
        Pelicula nueva = new Pelicula(dto.getTitulo());
        return ResponseEntity.status(HttpStatus.CREATED)
            .body(service.guardarPelicula(nueva));
    }
}
```

# Trampas Comunes en Arquitectura de Capas

* **Exponer Entidades del Dominio:** Enviar entidades JPA directo al cliente sin DTOs, arriesgando fallas de seguridad (*Overposting*).
* **Lógica en el Controlador:** Validar reglas complejas dentro de los controladores en lugar de centralizarlas en la capa `@Service`.
* **Consultas SQL en Capas Superiores:** Acoplar la capa de presentación a dependencias de consultas SQL nativas del motor.
