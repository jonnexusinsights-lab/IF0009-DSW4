# El Ecosistema Móvil: Duopolio

El mercado se divide en dos grandes arquitecturas y filosofías:

*   **🤖 Android (Google):** 
    *   Código abierto (Linux), alta fragmentación de hardware.
    *   Lenguajes nativos: **Kotlin** y Java.
    *   Tienda: Google Play (permite Sideloading).
*   **🍎 iOS (Apple):** 
    *   Código cerrado (Unix), hardware homogéneo (iPhone/iPad).
    *   Lenguajes nativos: **Swift** y Objective-C.
    *   Tienda: App Store (Estrictamente controlada).

---

# ¿Cómo construir la aplicación? (Enfoques)

### 1. Desarrollo Nativo
Se usan los lenguajes oficiales (Swift/Kotlin). Máximo rendimiento, pero se requieren dos bases de código y dos equipos de desarrollo separados.

### 2. Multiplataforma (Cross-Platform)
Una sola base de código para iOS y Android.
*   **React Native:** Usa un puente (JS Bridge) para hablar con botones nativos.
*   **Flutter:** Usa su propio motor de renderizado (Skia/Impeller) dibujando cada píxel a 60/120 fps.

### 3. PWA (Progressive Web Apps)
Páginas web que funcionan offline. Limitado acceso a hardware.

---

# El Ciclo de Vida: No eres dueño de la memoria

A diferencia del software de escritorio, en móviles **el Sistema Operativo es el rey**. Puede matar tu aplicación en cualquier momento.

### Android (Activity)
`onCreate()` -> `onStart()` -> `onResume()` -> (El usuario contesta una llamada) -> `onPause()` -> `onStop()` -> `onDestroy()`.

### iOS (ViewController)
`viewDidLoad()` -> `viewWillAppear()` -> `viewDidAppear()` -> `viewWillDisappear()` -> `viewDidDisappear()`.

💡 **Regla de oro:** Siempre guarda el estado y cancela tareas de red en `onPause`/`viewWillDisappear`.

---

# Restricciones Físicas y de UX

Programar para móviles requiere cambiar la mentalidad web:

1.  **🔋 Batería y Calor:** Tareas pesadas bloquean el UI y agotan la batería. Todo debe ser asíncrono.
2.  **👆 "Fat Finger Problem":** Los usuarios tocan con el dedo, no con un puntero. Todo botón debe ser de al menos **44x44 píxeles**.
3.  **🚫 No hay Hover:** No existe el evento de "pasar el mouse por encima". Las interacciones son Taps, Swipes y Long Presses.
4.  **📶 Red Inestable (Offline-first):** La app debe soportar transiciones en túneles o pérdida de señal. Use cachés locales (SQLite).

---

# Resumen: Ingeniería de Restricciones

El desarrollo móvil es **"Ingeniería de Restricciones"**.

Debemos entregar experiencias fluidas de 60 FPS, en pantallas diminutas, consumiendo la menor cantidad de batería posible, asumiendo que la red fallará, y bajo un sistema operativo que intentará destruir nuestra app para recuperar memoria RAM en cualquier momento.
