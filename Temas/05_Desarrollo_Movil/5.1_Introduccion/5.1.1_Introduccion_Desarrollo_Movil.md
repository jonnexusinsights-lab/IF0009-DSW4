# Tema 5.1.1: Introducción General al Desarrollo Móvil

El desarrollo de aplicaciones móviles es una disciplina única dentro de la ingeniería de software. A diferencia del desarrollo web, donde el cliente es un navegador que estandariza muchas interacciones, el desarrollo móvil requiere una interacción mucho más cercana con el sistema operativo anfitrión (Android o iOS) y el hardware del dispositivo.

---

## 1. Ecosistemas: iOS vs. Android

El mercado móvil está dominado por un duopolio: **Android (Google)** e **iOS (Apple)**. 

### 1.1 Android
*   **Base:** Sistema operativo de código abierto basado en el núcleo de Linux.
*   **Lenguajes Nativos:** Kotlin (oficial, preferido) y Java (heredado).
*   **Fragmentación:** Existe una alta fragmentación de hardware (miles de fabricantes) y de versiones de SO, lo que hace que las pruebas y la optimización de UI sean complejas.
*   **Distribución:** Principalmente a través de Google Play Store, pero permite "sideloading" (instalar APKs desde cualquier fuente).

### 1.2 iOS
*   **Base:** Sistema operativo cerrado basado en Unix (Darwin).
*   **Lenguajes Nativos:** Swift (oficial, moderno) y Objective-C (heredado).
*   **Homogeneidad:** El hardware es fabricado exclusivamente por Apple. La adopción de la última versión del SO es altísima (usualmente superior al 80% en los primeros meses).
*   **Distribución:** Estrictamente a través de la Apple App Store (aunque regulaciones europeas como la DMA están forzando aperturas recientes).

---

## 2. Enfoques de Desarrollo: Nativo vs. Multiplataforma

A la hora de iniciar un proyecto, la arquitectura tecnológica es la decisión más importante.

### 2.1 Desarrollo Nativo
Implica escribir código específico para cada plataforma utilizando las herramientas oficiales (Android Studio / Xcode).
*   **Ventajas:** Máximo rendimiento, acceso total al hardware (sensores, cámara, bluetooth), adopción inmediata de nuevas características del SO.
*   **Desventajas:** Requiere dos equipos de desarrollo distintos (costos x2), el mantenimiento y la sincronización de *features* entre plataformas es difícil.

### 2.2 Desarrollo Multiplataforma (Cross-Platform)
Consiste en escribir el código fuente una sola vez y compilarlo (o interpretarlo) para ambas plataformas.
*   **React Native (Meta):** Utiliza JavaScript/TypeScript. Un "puente" (bridge) comunica el hilo de JS con los componentes nativos OEM del dispositivo.
*   **Flutter (Google):** Utiliza Dart. No usa componentes nativos (OEM), sino que tiene su propio motor de renderizado (Skia / Impeller) que dibuja píxel por píxel, logrando 60 o 120 FPS de forma nativa sin pasar por un bridge.

### 2.3 Progressive Web Apps (PWA)
Son aplicaciones web (HTML/CSS/JS) que utilizan Service Workers para ejecutarse offline y pueden ser "instaladas" en la pantalla de inicio. No entran a las tiendas de aplicaciones tradicionales y tienen acceso limitado al hardware nativo.

## 3. Arquitecturas y Ciclo de Vida Móvil

Las aplicaciones móviles no se ejecutan linealmente; son gestionadas por el Sistema Operativo, que puede detenerlas o destruirlas en cualquier momento para liberar memoria.

### 3.1 Android: Activities y Fragments
*   **Activity:** Representa una pantalla única con una interfaz de usuario.
*   **Fragment:** Es un componente modular y reutilizable que vive dentro de una Activity.
*   **Ciclo de Vida:** `onCreate()` -> `onStart()` -> `onResume()` (app visible y activa). Si el usuario recibe una llamada, pasa a `onPause()`. Si abre otra app, pasa a `onStop()`. Si el SO necesita memoria, llama a `onDestroy()`.

### 3.2 iOS: ViewControllers
*   **UIViewController:** Gestiona una vista o un conjunto de vistas.
*   **Ciclo de Vida:** `viewDidLoad()` -> `viewWillAppear()` -> `viewDidAppear()`. Cuando la pantalla desaparece: `viewWillDisappear()` -> `viewDidDisappear()`.

Comprender el ciclo de vida es crucial para no dejar procesos consumiendo batería en segundo plano (memory leaks) y para guardar el estado del usuario antes de que el SO destruya la aplicación.

## 4. Restricciones y Principios UI/UX en Móviles

El desarrollo móvil opera bajo restricciones físicas que no existen en el escritorio:

1.  **Batería y Rendimiento Térmico:** Tareas pesadas (ej. procesamiento de imágenes, minería, pooling HTTP constante) agotarán la batería y calentarán el dispositivo. Todo procesamiento intensivo debe delegarse a la nube o ejecutarse en hilos secundarios (Background Threads / Isolates) usando APIs eficientes del SO (como WorkManager).
2.  **Pantalla (Screen Size):** El espacio es limitado. La información debe ser jerárquica. Se utilizan patrones de navegación como *Bottom Navigation Bars*, *Drawers* (menús laterales) y *Tabs*.
3.  **Táctil vs. Clic:** El dedo humano es impreciso ("Fat finger problem"). Los botones (Touch targets) deben tener un tamaño mínimo de **44x44 pt (iOS)** o **48x48 dp (Android)**. No existe el estado `hover` (pasar el mouse), por lo que las interacciones se basan en toques (taps), pulsaciones largas (long presses) y gestos de deslizamiento (swipes).
4.  **Red Inestable:** Los usuarios móviles atraviesan zonas de baja cobertura o pierden señal en elevadores. Las aplicaciones deben ser **Offline-First**, almacenando datos en cachés locales (SQLite, SharedPreferences) y mostrando estados de carga (skeletons, spinners) de forma elegante.

---

## 5. Conclusión

El éxito de una aplicación móvil no depende únicamente de su código, sino de cómo respeta las directrices del Sistema Operativo y las limitaciones de hardware. Ya sea utilizando un enfoque nativo puro o un framework multiplataforma como Flutter, el ingeniero debe diseñar siempre pensando en el ciclo de vida de la aplicación y la experiencia del usuario (batería, gestos, conectividad).
