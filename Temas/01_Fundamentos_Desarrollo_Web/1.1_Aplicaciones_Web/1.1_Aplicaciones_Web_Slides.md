# ¿Qué es una Aplicación Web?

* Es un **sistema de software distribuido** que permite la ejecución de tareas lógicas y la interacción de datos a través de una red (Internet/Intranet).
* Se ejecuta en una arquitectura desacoplada:
  * **Front-end (Cliente):** Corre en el navegador web del usuario final.
  * **Back-end (Servidor):** Corre en servidores remotos locales o en la nube.
* Utiliza protocolos estándar de comunicación (HTTP/HTTPS) para intercambiar información sin requerir instalaciones de software de escritorio específicas en el cliente.

# La Arquitectura Cliente-Servidor

Es el modelo de diseño de software subyacente de la Web:

* **El Cliente:** Es el demandante de recursos. Captura las interacciones del usuario, realiza validaciones sintácticas básicas de UI y envía solicitudes formales al servidor.
* **El Servidor:** Espera de forma pasiva las peticiones. Al recibir una, ejecuta la lógica de negocios, gestiona la persistencia de datos y devuelve un resultado.
* **El Mensajero:** La comunicación se orquesta a través de mensajes estandarizados llamados **Peticiones (Requests)** y **Respuestas (Responses)**.

# La Analogía del Restaurante

Para comprender intuitivamente este flujo distribuido:

* **El Cliente (Comensal):** Se sienta a la mesa y visualiza el menú (la interfaz gráfica). Elige un platillo de su preferencia.
* **El Protocolo HTTP/HTTPS (El Mesero):** Toma la orden escrita (la petición), la traslada a la cocina y regresa con el platillo preparado (la respuesta).
* **El Servidor (La Cocina):** Ejecuta la receta (lógica de negocio), consulta la bodega de ingredientes (base de datos) y prepara la comida en su formato final.
* **Aislamiento de Lógica:** El comensal nunca ingresa a la cocina por motivos de orden e higiene (seguridad y desacoplamiento).

# Evolución de la Web: Era 1.0

## Web Estática (Década de 1990)
* El servidor web actuaba únicamente como un **despachador de archivos de disco** (.html, .css, imágenes).
* Al solicitar una dirección web, el servidor leía el archivo correspondiente en el almacenamiento local y lo transfería de vuelta.
* **Limitaciones:**
  * Contenido plano e idéntico para todos los usuarios.
  * Sin bases de datos ni lógica dinámica interactiva.
  * Modificar información requería editar archivos manualmente y volver a subirlos al servidor.

# Evolución de la Web: Era 2.0

## Web Dinámica y Server-Side Rendering (Década de 2000)
* Incorporación de lenguajes del lado del servidor (PHP, ASP, Java Servlets) conectados a bases de datos relacionales (SQL).
* **Server-Side Rendering (SSR):** El servidor procesaba la petición, consultaba la base de datos y construía dinámicamente un documento HTML personalizado en caliente antes de enviarlo al cliente.
* **AJAX (2005):** Permitió actualizar partes individuales de la pantalla de forma asíncrona mediante JavaScript sin tener que recargar toda la página web por completo.

# Evolución de la Web: Era SPA y APIs

## Single Page Applications (SPA) y Servicios REST (Actualidad)
* El servidor se desacopla completamente del renderizado de interfaces.
* **Flujo SPA (Angular, React):** El servidor despacha un cascarón HTML mínimo y archivos JavaScript en la carga inicial. El framework en el navegador maneja la navegación interna y redibuja la UI dinámicamente.
* **APIs RESTful:** La comunicación posterior ocurre mediante peticiones AJAX intercambiando únicamente datos en bruto estructurados en formato **JSON**.

# El Ciclo de Vida de una Petición HTTP

```
[ Cliente ] --(1. Petición HTTP)--> [ Servidor Web (Node.js/ASP.NET) ]
     ^                                             │
     │                                     (2. Consulta datos)
     │                                             ▼
[ Navegador ] <--(3. Respuesta HTTP)-- [ Base de Datos ]
```

1. **Petición (Request):** Contiene el método HTTP (`GET`, `POST`, `PUT`, `DELETE`), la URI del recurso, encabezados (Headers) y opcionalmente un cuerpo de datos (Body).
2. **Procesamiento:** El servidor valida la solicitud, ejecuta lógica e interactúa con los motores de almacenamiento.
3. **Respuesta (Response):** Contiene un código de estado (ej: `200 OK`, `404 Not Found`), encabezados de tipo de contenido y el cuerpo.

# Ejemplo Técnico: Creación de un Servidor Nativo

A continuación se presenta un servidor web mínimo en Node.js que ilustra cómo interceptar peticiones y retornar contenido adaptado dinámicamente:

```javascript
const http = require('http');

const server = http.createServer((request, response) => {
    // Definición de CORS para autorizar conexiones remotas
    response.setHeader('Access-Control-Allow-Origin', '*');

    if (request.url === '/api/info' && request.method === 'GET') {
        response.writeHead(200, { 'Content-Type': 'application/json' });
        response.end(JSON.stringify({ curso: "IF0009", tema: "1.1 Web Apps" }));
    } else {
        response.writeHead(404, { 'Content-Type': 'application/json' });
        response.end(JSON.stringify({ error: "Recurso no encontrado" }));
    }
});

server.listen(3000, () => console.log('Escuchando en puerto 3000...'));
```

# Trampas Comunes en Arquitectura Web (Gotchas)

* **Vulnerabilidades de CORS:** Bloqueo de peticiones por parte de los navegadores si la API REST del servidor no incluye explícitamente encabezados CORS correctos permitiendo el dominio del front-end.
* **Semántica HTTP Rota:** Retornar códigos de estado `200 OK` en respuestas que informan un error interno del sistema, rompiendo los estándares de REST.
* **Almacenamiento de Sesiones del Lado del Servidor (Stateful):** Almacenar sesiones en la memoria del servidor imposibilita el escalado horizontal tras un balanceador de carga. Las APIs modernas deben ser **stateless** (sin estado).
