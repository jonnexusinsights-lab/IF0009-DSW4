# ¿Qué es una Aplicación Web Moderna?

* Es un **sistema de software distribuido** estructurado sobre una arquitectura desacoplada para interactuar a través de redes locales o Internet.
* **Componentes Principales:**
  * **Cliente (Front-end):** Interfaz gráfica interactiva que se ejecuta en el navegador web del usuario.
    * Interpreta HTML.
    * Interpreta CSS.
    * Interpreta JavaScript.
  * **Servidor (Back-end):** Ejecuta:
    * Lógica densa de negocios.
    * Validación de datos de entrada.
    * Control de accesos y seguridad.
    * Persistencia remota.
  * **Protocolo de Comunicación:** Conjunto de reglas estandarizadas de transporte (HTTP/HTTPS) que rigen el intercambio de información.

# Anatomía del Modelo Cliente-Servidor

* **Desacoplamiento Operativo:** El cliente y el servidor tienen responsabilidades segregadas. El cliente no accede a las bases de datos directamente por razones de seguridad y abstracción.
* **Flujo Transaccional:**
  1. El **Cliente** inicia de forma activa una conexión para enviar una **Petición (Request)**.
  2. El **Servidor** (escuchando pasivamente en un puerto TCP) intercepta la petición, procesa la lógica asociada y devuelve una **Respuesta (Response)**.
  3. La conexión se mantiene abierta o se cierra según los encabezados de conexión del protocolo HTTP.

# La Analogía del Restaurante de Alta Cocina

* **El Comensal (El Cliente):** Visualiza el menú (UI en navegador) y selecciona un plato. No cocina él mismo ni conoce las recetas internas.
* **El Mesero (Protocolo HTTP/HTTPS):** Transporta la orden (Petición) desde la mesa hasta la cocina, garantizando que el mensaje siga el estándar de la casa. Luego trae de vuelta el platillo terminado (Respuesta).
* **La Cocina (El Servidor/Base de Datos):** Procesa la orden de forma aislada. Consulta la despensa (Base de Datos) e implementa las recetas (Lógica de negocio).
* **Seguridad:** Mantener a los comensales fuera de la cocina previene incidentes (inyecciones de código, accesos indebidos de datos).

# Evolución de la Web: Era 1.0 (Estática)

* **Características (Década de 1990):**
  * El servidor web era un simple despachador de archivos de texto almacenados en disco (`.html`, `.css`).
  * Sin bases de datos dinámicas ni lógica interactiva compleja.
  * Todo usuario que visitaba una dirección URL recibía exactamente el mismo archivo binario.
* **Limitaciones:**
  * Actualizar información implicaba reescribir código HTML y subir manualmente los archivos de nuevo a través de protocolos como FTP.
  * Imposibilidad de manejar estados de sesión complejos:
    * Carritos de compra.
    * Perfiles de usuario.

# Evolución de la Web: Era 2.0 (SSR y AJAX)

* **Server-Side Rendering (SSR - Década de 2000):**
  * Introducción de bases de datos relacionales y lenguajes backend:
    * Java Servlets.
    * PHP.
    * ASP.
  * El servidor procesa la lógica e inyecta dinámicamente datos en plantillas HTML antes de transmitirlas al cliente.
* **Revolución AJAX (2005):**
  * *Asynchronous JavaScript and XML* habilitó la actualización asíncrona de partes específicas de la interfaz sin necesidad de refrescar toda la ventana del navegador.
  * Redujo el consumo de ancho de banda y mejoró la usabilidad.

# Evolución de la Web: Era SPA y APIs

* **Single-Page Applications (SPA - Década de 2010):**
  * El servidor únicamente despacha una plantilla HTML vacía y paquetes JavaScript/TypeScript iniciales.
  * Frameworks de cliente (ej. **Angular**) manejan el enrutamiento interno y redibujan dinámicamente el DOM.
* **Interfaces de Programación de Aplicaciones (APIs):**
  * El servidor de backend se desacopla del diseño gráfico.
  * Se convierte en una **API RESTful** que solo intercambia información cruda estructurada.
  * El formato estándar de intercambio es **JSON**, reduciendo drásticamente la carga de la red.

# El Protocolo HTTP: Anatomía del Request

Cada petición enviada por el cliente al servidor contiene:
* **Método HTTP (Verbos):** Define la acción semántica:
  * `GET`: Solicitar un recurso sin efectos colaterales en el servidor.
  * `POST`: Crear un nuevo recurso en el servidor.
  * `PUT`: Actualizar un recurso existente.
  * `DELETE`: Eliminar un recurso del sistema.
* **URI / URL:** Dirección de destino del recurso.
* **Headers (Encabezados):** Metadatos de la petición:
  * `Content-Type` (ej. `application/json`).
  * `Authorization` (ej. `Bearer <token>`).
* **Body (Cuerpo):** Carga útil de datos (payload), común en `POST` o `PUT`.

# El Protocolo HTTP: Anatomía del Response (Códigos de Estado)

Cada respuesta devuelta por el servidor contiene metadatos y un estado de ejecución:
* **Código de Estado HTTP (Status Codes):**
  * `2xx` (Éxito):
    * `200 OK` (Petición resuelta con éxito).
    * `201 Created` (Recurso creado con éxito).
  * `3xx` (Redirección):
    * `301 Moved Permanently` (Redirección a nueva URI).
  * `4xx` (Error del Cliente):
    * `400 Bad Request` (Sintaxis inválida o datos incorrectos).
    * `401 Unauthorized` (Autenticación requerida).
    * `404 Not Found` (Recurso inexistente).
  * `5xx` (Error del Servidor):
    * `500 Internal Server Error` (Excepción no controlada en el backend).

# El Protocolo HTTP: Anatomía del Response (Encabezados y Cuerpo)

* **Headers (Encabezados de Respuesta):** Metadatos clave enviados por el servidor:
  * `Content-Type` (ej. `application/json; charset=utf-8`).
  * `Access-Control-Allow-Origin` (Permisos CORS).
  * `Set-Cookie` (Creación de cookies de sesión en el cliente).
* **Body (Cuerpo de la Respuesta):** La carga útil (*payload*) del recurso solicitado:
  * Estructuras web: HTML, CSS, JavaScript.
  * Datos crudos: JSON (estándar para APIs de Angular y móviles).
  * Binarios: Imágenes, PDFs o documentos descargables.

# Implementación en Java: Servidor HTTP Nativo

A nivel de red, un servidor se encarga de abrir sockets y enrutar las peticiones. En Java se logra mediante `com.sun.net.httpserver.HttpServer`:

```java
import com.sun.net.httpserver.HttpServer;
import com.sun.net.httpserver.HttpHandler;
import com.sun.net.httpserver.HttpExchange;
import java.io.IOException;
import java.io.OutputStream;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;

public class ServidorWeb {
    public static void main(String[] args) throws IOException {
        int puerto = 3000;
        HttpServer server = HttpServer.create(new InetSocketAddress(puerto), 0);
        
        // Registrar rutas (Contextos) y asociar manejadores
        server.createContext("/api/info", new InfoHandler());
        server.createContext("/", new HomeHandler());
        
        server.setExecutor(null); // Usar ejecutor predeterminado
        System.out.println("Servidor Java escuchando en puerto " + puerto);
        server.start();
    }
    // (Manejadores de rutas detallados en la siguiente diapositiva...)
}
```

# Implementación en Java: Manejadores de Rutas

A continuación se detalla cómo procesar los objetos de petición y respuesta usando `HttpHandler`:

```java
static class InfoHandler implements HttpHandler {
    @Override
    public void handle(HttpExchange exchange) throws IOException {
        if ("GET".equalsIgnoreCase(exchange.getRequestMethod())) {
            // Configurar encabezados CORS y tipo de respuesta
            exchange.getResponseHeaders().set("Content-Type", "application/json; charset=utf-8");
            exchange.getResponseHeaders().set("Access-Control-Allow-Origin", "*");
            
            String jsonResponse = "{\"curso\": \"IF0009\", \"servidor\": \"Java HttpServer\"}";
            byte[] responseBytes = jsonResponse.getBytes(StandardCharsets.UTF_8);
            
            // Enviar headers (Status 200) y longitud del payload
            exchange.sendResponseHeaders(200, responseBytes.length);
            try (OutputStream os = exchange.getResponseBody()) {
                os.write(responseBytes); // Escribir en el stream de respuesta
            }
        } else {
            exchange.sendResponseHeaders(405, -1); // 405 Method Not Allowed
        }
    }
}
```

# Trampa Arquitectónica #1: Errores de CORS

* **CORS (Cross-Origin Resource Sharing):**
  * Mecanismo de seguridad implementado por los navegadores web.
  * Evita llamadas cruzadas no autorizadas desde un origen cliente hacia un origen servidor.
  * **Ejemplo de conflicto:**
    * Origen Cliente: `http://localhost:4200` (Angular)
    * Origen Servidor: `http://localhost:3000` (API Java)
* **Solución:**
  * El servidor debe agregar encabezados de respuesta CORS válidos:
    * `Access-Control-Allow-Origin: *` o el dominio de confianza del cliente.

# Trampa Arquitectónica #2: Servidores Stateful

* **Servidor Stateful (Con Estado):**
  * Almazena datos de sesión del usuario activo directamente en la memoria caché del proceso del servidor de aplicaciones.
  * **Problema:** Si el tráfico aumenta y se requiere duplicar los servidores backend detrás de un balanceador de carga, el usuario perderá su sesión si es redirigido a otro nodo.
* **Solución (Arquitectura Stateless):**
  * Las APIs modernas deben ser sin estado.
  * Toda información de autenticación se envía en cada request en forma de token firmado.
  * El estándar de la industria es el uso de **JWT** (JSON Web Tokens).
