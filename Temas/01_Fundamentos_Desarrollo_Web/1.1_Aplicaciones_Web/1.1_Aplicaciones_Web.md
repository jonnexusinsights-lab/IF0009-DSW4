# Tema 1.1: Aplicaciones Web — Evolución y Arquitectura Cliente-Servidor

## Resumen
En esta lectura usted estudiará los fundamentos de las aplicaciones web, analizando su evolución histórica desde los documentos estáticos hasta las arquitecturas modernas. Asimismo, comprenderá el funcionamiento del modelo Cliente-Servidor y el ciclo de vida de una petición HTTP/HTTPS, utilizando ejemplos prácticos implementados en el lenguaje de programación **Java** para comprender la comunicación a nivel de red y protocolo.

---

## Concepto Principal (El 'Qué')

Una **aplicación web** es un sistema de software distribuido cuyas aplicaciones cliente y servidor interactúan a través de una red informática (comúnmente la Internet) utilizando protocolos estándar de comunicación. A diferencia de las aplicaciones de escritorio tradicionales, la interfaz de usuario se renderiza en un navegador web, mientras que el almacenamiento y el procesamiento lógico denso ocurren en servidores remotos.

### La Arquitectura Cliente-Servidor
Esta arquitectura divide las tareas y cargas de trabajo entre proveedores de recursos o servicios (llamados **servidores**) y demandantes de servicios (llamados **clientes**).

1. **El Cliente (Front-end / User Agent):** Es el agente de usuario que realiza peticiones de servicio. Comúnmente es un navegador web (Chrome, Firefox, Safari) que interpreta código HTML, CSS y JavaScript para pintar la interfaz gráfica y responder a las interacciones de los usuarios.
2. **El Servidor (Back-end):** Es el programa o computadora física que espera de forma pasiva las conexiones entrantes de los clientes. Al recibir una solicitud, procesa los datos correspondientes (ejecutando lógica de negocios y consultas a bases de datos) y retorna una respuesta.
3. **El Medio de Comunicación (Red y Protocolos):** La interacción se da a través de redes TCP/IP utilizando el protocolo **HTTP (Hypertext Transfer Protocol)** o su versión segura **HTTPS (HTTP Secure)**.

### Evolución Histórica de las Aplicaciones Web
La Web ha transitado por diversas eras técnicas que usted debe diferenciar:

* **Web 1.0 (Web Estática - Década de 1990):** Consistía principalmente en archivos HTML estáticos enlazados por hipervínculos. El servidor web actuaba únicamente como un despachador de archivos de disco. No existía base de datos asociada ni interacción dinámica compleja.
* **Web 2.0 (Web Dinámica e Interactiva - Década de 2000):** Se introdujeron lenguajes del lado del servidor (como PHP, ASP, Java Servlets) y bases de datos relacionales. Las páginas se generaban dinámicamente en el servidor en cada petición (*Server-Side Rendering* o SSR). Posteriormente, con la llegada de **AJAX (Asynchronous JavaScript and XML)** en 2005, los clientes pudieron realizar peticiones en segundo plano sin recargar toda la página web, abriendo la puerta a la Web interactiva.
* **Arquitecturas SPA y APIs modernas (Década de 2010 en adelante):** La lógica de renderizado se trasladó del servidor al navegador mediante frameworks de cliente (*Single Page Applications* o SPA, como Angular, React o Vue). El servidor pasó a actuar como un proveedor de servicios puros mediante interfaces de programación de aplicaciones (**APIs RESTful** o **GraphQL**), intercambiando únicamente datos estructurados (comúnmente en formato **JSON**).

## Analogía (La Intuición)

Considere el funcionamiento de un **restaurante de comida a la carta**:
* **Usted (el cliente)** se sienta a la mesa y examina el menú (la interfaz web).
* **El mesero (el protocolo HTTP/HTTPS)** es el mesero que lleva su pedido (la petición) a la cocina y trae su platillo (la respuesta).
* **La cocina (el servidor web y de base de datos)** procesa su pedido combinando ingredientes, ejecutando recetas (lógica de negocio) y extrayendo insumos de la alacena (base de datos) para preparar el platillo final. 
* Usted no entra a la cocina a preparar la comida; solo interactúa con el mesero para enviar órdenes y recibir respuestas.

## Ejemplo de Código e Implementación (El 'Cómo')

Para ilustrar este modelo Cliente-Servidor en el desarrollo de software moderno utilizando **Java**, a continuación se presenta la creación de un servidor HTTP ligero empleando la clase nativa del JDK `com.sun.net.httpserver.HttpServer`. Esto demuestra el control directo de puertos y el formateo manual de las respuestas web.

```java
import com.sun.net.httpserver.HttpServer;
import com.sun.net.httpserver.HttpHandler;
import com.sun.net.httpserver.HttpExchange;
import java.io.IOException;
import java.io.OutputStream;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;
import java.time.Instant;

public class ServidorWeb {
    public static void main(String[] args) throws IOException {
        int puerto = 3000;
        
        // Crear el servidor HTTP escuchando en el puerto 3000
        HttpServer server = HttpServer.create(new InetSocketAddress(puerto), 0);
        
        // Registrar contexto para simular un Endpoint de API REST
        server.createContext("/api/info", new InfoHandler());
        
        // Registrar contexto para despachar una página HTML de inicio
        server.createContext("/", new HomeHandler());
        
        // Configurar el ejecutor por defecto y arrancar el servidor
        server.setExecutor(null); 
        System.out.println("Servidor Java activo en http://localhost:" + puerto);
        server.start();
    }

    // Manejador para solicitudes a la API (/api/info)
    static class InfoHandler implements HttpHandler {
        @Override
        public void handle(HttpExchange exchange) throws IOException {
            // Verificar que el método sea GET
            if ("GET".equalsIgnoreCase(exchange.getRequestMethod())) {
                // Agregar encabezados CORS y tipo de respuesta JSON
                exchange.getResponseHeaders().set("Content-Type", "application/json; charset=utf-8");
                exchange.getResponseHeaders().set("Access-Control-Allow-Origin", "*");
                
                String jsonResponse = "{"
                        + "\"curso\": \"IF0009 - Desarrollo de Software IV\","
                        + "\"tema\": \"1.1 Aplicaciones Web\","
                        + "\"servidor\": \"Java HttpServer Nativo\","
                        + "\"fecha\": \"" + Instant.now().toString() + "\""
                        + "}";
                
                byte[] responseBytes = jsonResponse.getBytes(StandardCharsets.UTF_8);
                exchange.sendResponseHeaders(200, responseBytes.length);
                try (OutputStream os = exchange.getResponseBody()) {
                    os.write(responseBytes);
                }
            } else {
                exchange.sendResponseHeaders(405, -1); // 405 Method Not Allowed
            }
        }
    }

    // Manejador para el despacho del HTML principal (/)
    static class HomeHandler implements HttpHandler {
        @Override
        public void handle(HttpExchange exchange) throws IOException {
            if ("GET".equalsIgnoreCase(exchange.getRequestMethod())) {
                exchange.getResponseHeaders().set("Content-Type", "text/html; charset=utf-8");
                
                String htmlResponse = "<!DOCTYPE html>"
                        + "<html lang=\"es\">"
                        + "<head>"
                        + "    <meta charset=\"UTF-8\">"
                        + "    <title>Servidor de Prueba UCR</title>"
                        + "    <style>"
                        + "        body { font-family: sans-serif; background: #0f172a; color: #f8fafc; text-align: center; padding-top: 50px; }"
                        + "        .card { background: #1e293b; padding: 30px; border-radius: 12px; display: inline-block; box-shadow: 0 10px 15px rgba(0,0,0,0.3); border: 1px solid #334155; }"
                        + "        h1 { color: #38bdf8; }"
                        + "    </style>"
                        + "</head>"
                        + "<body>"
                        + "    <div class=\"card\">"
                        + "        <h1>Servidor Web en Java</h1>"
                        + "        <p>Conexión exitosa al curso <strong>IF0009 - Desarrollo de Software IV</strong>.</p>"
                        + "    </div>"
                        + "</body>"
                        + "</html>";
                
                byte[] responseBytes = htmlResponse.getBytes(StandardCharsets.UTF_8);
                exchange.sendResponseHeaders(200, responseBytes.length);
                try (OutputStream os = exchange.getResponseBody()) {
                    os.write(responseBytes);
                }
            } else {
                exchange.sendResponseHeaders(405, -1);
            }
        }
    }
}
```

### Explicación del Código:
1. **`HttpServer.create(...)`**: Abre un socket TCP de escucha pasiva en el puerto `3000`.
2. **`createContext(...)`**: Enruta las peticiones de red hacia manejadores (`HttpHandler`) según el path solicitado, similar al concepto de enrutadores en frameworks modernos.
3. **`HttpExchange`**: Objeto que encapsula la petición (`getRequestMethod()`, `getRequestHeaders()`) y expone la respuesta mediante encabezados (`getResponseHeaders()`) y el canal de escritura (`getResponseBody()`).

## Trampas Comunes (Gotchas)

Al diseñar o depurar arquitecturas Cliente-Servidor, usted debe estar alerta a las siguientes fallas críticas:

1. **Errores de CORS (Cross-Origin Resource Sharing):** Cuando una aplicación SPA (cliente) servida desde `http://localhost:4200` intenta consumir una API REST (servidor) expuesta en `http://localhost:3000`, el navegador web bloqueará la petición por motivos de seguridad a menos que el servidor declare explícitamente en sus encabezados (`Access-Control-Allow-Origin`) que confía en dicho origen.
2. **Confusión en los Códigos de Estado HTTP:** Responder con código de éxito `200 OK` cuando internamente ocurrió un error de servidor (ej. un fallo de base de datos que debería retornar `500 Internal Server Error`) rompe la estandarización semántica del protocolo HTTP y dificulta el manejo de errores en el front-end.
3. **Asunción de Estado en Servidores (Stateful vs Stateless):** En la web moderna, las APIs de servicios web deben ser **stateless** (sin estado). Evite almacenar variables de sesión en memoria del servidor de aplicaciones, ya que esto impedirá escalar el backend horizontalmente usando balanceadores de carga. Utilice tokens JWT para transferir el estado de la sesión en cada request.
