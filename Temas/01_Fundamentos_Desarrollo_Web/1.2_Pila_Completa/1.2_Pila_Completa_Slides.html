¿Qué es el Desarrollo Full-Stack?

  • Representa la construcción integral de todas las capas lógicas y estructurales de una aplicación de software.
  • Divide la carga de trabajo en dos entornos de ejecución desacoplados:
    • El Back-end (Lado Servidor):
      • Procesamiento de datos y lógica dura.
    • El Front-end (Lado Cliente):
      • Interfaz visual y experiencia de interacción directa.
  • El ingeniero full-stack es el puente técnico que integra ambas capas mediante el dominio de bases de datos, APIs y frameworks cliente.

1.2.1 El Rol del Back-end (Servidor)

  • Es la capa de soporte de datos e infraestructura que corre de forma remota, invisible para el usuario.
  • Responsabilidades Clave:
    • Almacenar de forma segura el estado persistente del sistema.
    • Ejecutar reglas de cálculo e integridad empresarial.
    • Garantizar la seguridad de accesos y la gestión de sesiones.
    • Proveer interfaces de comunicación estandarizadas (APIs).
  • Entornos de Ejecución Populares:
    • Java JDK (Spring Boot).
    • .NET SDK (C# / ASP.NET).
    • Node.js runtime.

Componentes de un Back-end en Capas

  • Capa de Persistencia (Base de Datos):
    • Almacenamiento relacional (ej. PostgreSQL, SQL Server).
    • Consumo optimizado mediante ORMs (Mapeo Objeto-Relacional).
  • Capa de Lógica de Negocio (Servicios):
    • Clases aisladas que aplican las directrices comerciales reales, desacopladas de la base de datos.
  • Capa de Controladores (APIs):
    • Controladores REST que procesan las solicitudes de red, validan esquemas sintácticos y despachan respuestas HTTP.

1.2.2 El Rol del Front-end (Cliente)

  • Es la capa interactiva y de maquetación que se procesa directamente en el navegador del usuario final.
  • Responsabilidades Clave:
    • Desplegar el contenido semántico y la estructura visual.
    • Adaptar la visualización a múltiples dispositivos (Responsive Design).
    • Validar datos de formulario antes de transmitirlos.
    • Controlar la navegación interna de pantallas dinámicamente.
  • Tecnologías Clave:
    • HTML5 semántico.
    • CSS3 layouts responsivos.
    • JavaScript moderno (TypeScript) y frameworks (ej. Angular).

La Analogía del Teatro de Ópera

  • El Escenario y Actores (Front-end):
    • Es lo único visible para la audiencia. La decoración (CSS), los parlamentos interactivos (JavaScript) y la secuencia lógica del libreto (Angular) están diseñados para el cliente.
  • Bastidores y Control de Tramoyas (Back-end):
    • Área cerrada que da soporte real al show. Almacena utilería (datos) y maneja las poleas y la seguridad (lógica del servidor).
  • El Director (API REST):
    • Comunica en tiempo real lo que ocurre tras bambalinas hacia los actores en el escenario de forma estructurada.

Integración Práctica: Servidor Java API

Mapeamos un servidor HTTP básico en Java que escucha en el puerto 3000 y expone datos académicos de estudiante en formato JSON: 
import com.sun.net.httpserver.HttpServer;
import com.sun.net.httpserver.HttpHandler;
import com.sun.net.httpserver.HttpExchange;
import java.io.IOException;
import java.io.OutputStream;
import java.net.InetSocketAddress;

public class BackendServer {
    public static void main(String[] args) throws IOException {
        HttpServer server = HttpServer.create(new InetSocketAddress(3000), 0);
        server.createContext("/api/estudiante", new EstudianteHandler());
        server.setExecutor(null);
        server.start();
    }
    // (Manejador EstudianteHandler en diapositiva siguiente...)
}

Integración Práctica: Manejador Java JSON

Implementación del Handler que despacha datos estructurados habilitando CORS: 
static class EstudianteHandler implements HttpHandler {
    @Override
    public void handle(HttpExchange exchange) throws IOException {
        if ("GET".equalsIgnoreCase(exchange.getRequestMethod())) {
            // Headers de respuesta e inyección CORS para el cliente
            exchange.getResponseHeaders().set("Content-Type", "application/json");
            exchange.getResponseHeaders().set("Access-Control-Allow-Origin", "*");
            
            String jsonPayload = "{\"carnet\":\"C01234\",\"nombre\":\"Ana Pérez\",\"sede\":\"Paraíso\"}";
            byte[] responseBytes = jsonPayload.getBytes("UTF-8");
            
            exchange.sendResponseHeaders(200, responseBytes.length);
            try (OutputStream os = exchange.getResponseBody()) {
                os.write(responseBytes);
            }
        } else {
            exchange.sendResponseHeaders(405, -1);
        }
    }
}

Script Front-end ejecutado en navegador que utiliza la API Fetch nativa para comunicarse con la API de Java en segundo plano: 
<div class="card">

<script>
    function solicitarDatos() {
        const contenedor = document.getElementById('resultado');
        fetch('http://localhost:3000/api/estudiante')
            .then(res => res.json())
            .then(data => {
                contenedor.innerHTML = `<p>Estudiante: ${data.nombre} (${data.carnet})</p>`;
            })
            .catch(err => {
                contenedor.innerHTML = `<p style="color:red;">Error: ${err.message}</p>`;
            });
    }
</script>

Trampa Arquitectónica: Validaciones Redundantes

  • Falla de Confianza en el Cliente:
    • Asumir que si la validación sintáctica del formulario se ejecutó en JavaScript en el navegador, el servidor de base de datos está a salvo de datos dañados.
  • El Peligro Real:
    • Un atacante o script automatizado puede saltar la interfaz web y enviar peticiones directas HTTP corruptas o maliciosas a la API REST.
  • Solución de Pila Completa:
    • La regla de oro: Valide en el Front-end para mejorar la experiencia de usuario, pero valide siempre en el Back-end para asegurar la consistencia y seguridad del sistema.

Trampa Arquitectónica: Contract Mismatches

  • Definición de Contrato API:
    • Estructura de nombres y tipos acordada entre cliente y servidor (ej. formato JSON).
  • El Problema del Mismatch:
    • Si el equipo de Back-end decide renombrar la llave JSON nombre a nombreCompleto, el código del Front-end continuará buscando la propiedad original.
    • Esto resulta en campos en blanco (undefined) e incoherencias de datos en la UI.
  • Mitigación:
    • Estandarizar la documentación de la API mediante contratos dinámicos usando OpenAPI / Swagger y mockups compartidos.
