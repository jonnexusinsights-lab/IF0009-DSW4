# Tema 1.3: Tendencias en Arquitecturas de Aplicaciones Web — MPA, SPA, PWA y Aplicaciones Nativas

## Resumen
En esta lectura, usted estudiará las cuatro tendencias arquitectónicas principales en el desarrollo de software web y móvil moderno: **Multi-Page Applications (MPA)**, **Single-Page Applications (SPA)**, **Progressive Web Applications (PWA)** y **Aplicaciones Nativas**. Analizará sus diferencias estructurales, trade-offs de rendimiento, SEO, experiencia de usuario y entenderá cómo se implementan a nivel del servidor utilizando la plataforma **Java** con **Spring Boot**.

---

## Concepto Principal (El 'Qué')

La selección del tipo de arquitectura web influye directamente en el rendimiento de la aplicación, el tiempo de desarrollo, la indexación en buscadores (SEO) y la complejidad del despliegue:

1. **Multi-Page Applications (MPA - Aplicaciones Multi-Página):**
   Es la arquitectura web clásica. En este modelo, el ciclo de vida es impulsado enteramente por el servidor web. Cada clic de navegación o envío de formulario requiere que el cliente realice una petición HTTP completa al servidor. El servidor procesa la solicitud, consulta bases de datos y devuelve un nuevo documento HTML completamente renderizado. 
   * *Ventajas:* Excelente SEO nativo (el HTML ya viene con la metadata y contenido listo) y menor carga de procesamiento en el cliente.
   * *Desventajas:* Latencia de carga perceptible en cada transición y consumo de ancho de banda ineficiente.

2. **Single-Page Applications (SPA - Aplicaciones de Página Única):**
   En esta arquitectura, el navegador descarga un solo archivo HTML mínimo junto con hojas de estilo CSS y un gran bloque de JavaScript (usualmente compilado desde frameworks como Angular, React o Vue). La navegación no recarga la página física; en su lugar, JavaScript intercepta los eventos, altera el DOM de manera dinámica y solicita datos crudos (JSON) al servidor a través de APIs RESTful.
   * *Ventajas:* Transiciones de pantalla instantáneas (experiencia fluida estilo app de escritorio) y desacoplamiento limpio entre back-end y front-end.
   * *Desventajas:* Primer tiempo de carga lento y retos adicionales para la indexación web (SEO).

3. **Progressive Web Applications (PWA - Aplicaciones Web Progresivas):**
   Son aplicaciones web (SPA o MPA) mejoradas progresivamente para comportarse como aplicaciones móviles nativas. Utilizan APIs modernas del navegador como **Service Workers** (scripts que corren en segundo plano, actúan como proxy de red y controlan la caché para permitir funcionamiento offline) y un archivo **Web App Manifest** (JSON que describe la app para permitir instalarla en la pantalla de inicio del dispositivo).
   
4. **Aplicaciones Nativas / Híbridas (Native):**
   Desarrolladas específicamente para un sistema operativo móvil (iOS con Swift, Android con Kotlin) o multiplataforma (React Native o Flutter). Se compilan directamente al set de instrucciones del procesador de la máquina, permitiendo acceso irrestricto y de alto rendimiento a las APIs de hardware (sensores, GPS, cámaras).

```
Flujo de Renderizado:
MPA:  [Cliente] ── Petición (HTTP GET) ──> [Servidor (Renderiza HTML)] ── HTML Completo ──> [Cliente (Dibuja todo)]
SPA:  [Cliente] ── Petición (API REST) ──> [Servidor (Procesa Datos)]   ── Datos JSON   ──> [Cliente (Renderiza JS)]
```

## Analogía (La Intuición)

Imagine las arquitecturas web como diferentes formas de comprar y consumir **libros de recetas**:
* **MPA es un servicio postal tradicional de recetas:** Cada vez que usted quiere leer una receta nueva, le envía una carta al cartero (servidor) pidiéndole la receta de las lasañas. El cartero viaja a la oficina central, imprime la página completa en papel con la foto y las instrucciones, y se la entrega por correo físico (HTML). Si luego quiere la receta de galletas, debe enviar otra carta y esperar que llegue una nueva página completa.
* **SPA es un libro electrónico (Kindle) precargado:** Al encender el lector por primera vez (primera carga), usted descarga toda la estructura del libro (JavaScript/CSS del lector). Si quiere cambiar de receta, el lector cambia el texto de la pantalla de forma instantánea sin necesidad de comprar otro dispositivo físico, y solo se conecta a internet para descargar el texto bruto de los nuevos ingredientes (JSON).
* **PWA es un Kindle con memoria de almacenamiento offline:** Además de cambiar de receta al instante, el Kindle guarda copias de seguridad de las últimas recetas leídas en su memoria interna. Si se corta el internet en su cocina (pérdida de red), usted puede seguir leyendo las recetas guardadas porque el dispositivo las sirve desde su almacenamiento local (Service Worker).
* **Aplicación Nativa es contratar a un chef personal en casa:** El chef (app nativa) vive en su casa, habla el idioma de su familia (lenguaje de máquina nativo) y puede utilizar directamente todas las herramientas avanzadas de su cocina (cámara, GPS) de manera directa y optimizada sin intermediarios.

## Ejemplo de Código e Implementación (El 'Cómo')

En un sistema empresarial de pila completa con **Java**, es muy común que el servidor soporte ambas aproximaciones. A continuación, se detalla un controlador de **Spring Boot** que expone un endpoint clásico de **MPA** (renderizado de HTML mediante el motor de plantillas **Thymeleaf**) y un endpoint de **SPA** (que retorna datos crudos en formato JSON para que un framework como Angular los dibuje):

```java
package cr.ac.ucr.if0009.controller;

import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.ResponseBody;

import java.util.ArrayList;
import java.util.List;

// Definición de una clase de datos simulada
class Noticia {
    private String titulo;
    private String contenido;

    public Noticia(String titulo, String contenido) {
        this.titulo = titulo;
        this.contenido = contenido;
    }
    public String getTitulo() { return titulo; }
    public String getContenido() { return contenido; }
}

@Controller
@RequestMapping("/noticias")
public class NoticiasController {

    // Método helper para simular base de datos
    private List<Noticia> obtenerNoticiasDePrueba() {
        List<Noticia> lista = new ArrayList<>();
        lista.add(new Noticia("Lanzamiento PWA", "Nuestra aplicación web ahora es instalable offline."));
        lista.add(new Noticia("Migración a SPA", "El frontend ha sido migrado exitosamente a Angular."));
        return lista;
    }

    /**
     * Aproximación MPA (Multi-Page Application)
     * El servidor une los datos con la plantilla HTML en el backend y devuelve el documento compilado.
     */
    @GetMapping("/portal")
    public String verPortalNoticias(Model model) {
        // Adjuntar datos al modelo que Thymeleaf procesará
        model.addAttribute("noticias", obtenerNoticiasDePrueba());
        model.addAttribute("tituloPortal", "Portal Informativo (MPA)");
        
        // Retorna el nombre de la plantilla HTML física (ej. noticias_template.html)
        return "noticias_template"; 
    }

    /**
     * Aproximación SPA (Single-Page Application / API REST)
     * El servidor se limita a responder la data cruda estructurada en JSON.
     * JavaScript en el cliente (ej. Angular) se encargará de consumir e inyectar esta data en el DOM.
     */
    @GetMapping("/api")
    @ResponseBody // Indica a Spring que serialice la lista a JSON directamente en el cuerpo HTTP
    public List<Noticia> obtenerNoticiasJson() {
        return obtenerNoticiasDePrueba();
    }
}
```

### Explicación Línea por Línea
* **`@Controller`**: Anotación de Spring que registra la clase en el contenedor de dependencias como un controlador de peticiones web.
* **`verPortalNoticias(Model model)`**: Este endpoint atiende la arquitectura **MPA**. Toma los datos, los inyecta en el objeto `Model` y retorna `"noticias_template"`. Spring Boot buscará el archivo físico `src/main/resources/templates/noticias_template.html`, ejecutará el renderizado de etiquetas en el servidor y enviará el HTML final compilado al cliente.
* **`@ResponseBody` y `obtenerNoticiasJson()`**: Atiende la arquitectura **SPA**. Gracias a la anotación `@ResponseBody`, Spring pasa por alto los motores de plantillas HTML y utiliza una biblioteca interna (Jackson) para convertir la lista de Java a un arreglo JSON: `[{"titulo":"Lanzamiento PWA", ...}, ...]`, devolviéndolo con el encabezado de contenido `application/json`.

## Trampas Comunes (Gotchas)

1. **Vulnerar el SEO en SPAs (Client-Side Rendering):**
   Si usted construye un sitio corporativo puramente como una SPA y no implementa estrategias de hidratación o renderizado híbrido (SSR - Server-Side Rendering), los robots de búsqueda de menor calidad podrían indexar una página web en blanco, ya que no ejecutan el JavaScript que carga las noticias desde la API.
   * *Solución:* Para landing pages o sitios donde el SEO es crítico, use arquitecturas MPA tradicionales, o implemente frameworks modernos de SSR (como Angular SSR o Next.js) que ejecutan la primera carga en el servidor antes de entregar el control a la SPA.

2. **Inconsistencia de Estados en PWAs con Service Workers (Caching agresivo):**
   Los Service Workers tienden a cachear archivos de forma extremadamente agresiva. Si usted actualiza el código JS de su aplicación en el servidor, los usuarios recurrentes podrían seguir visualizando la versión vieja de la app porque el Service Worker carga los archivos locales cacheados antes de consultar a la red.
   * *Solución:* Implemente estrategias de versionado de nombres de archivos (*hash* en el bundling) e incluya rutinas de detección de actualizaciones en el registro del Service Worker para forzar la recarga cuando se detecte un nuevo script.
