# Tema 1.4: Criterios de Selección de Stacks Tecnológicos y Frameworks de Software

## Resumen
En esta lectura, usted estudiará la definición formal de un **Framework de Software** y su diferencia fundamental con una **Biblioteca (Library)**, a través del concepto de **Inversión de Control (IoC)**. Además, analizará los principales criterios técnicos y de negocio para evaluar y seleccionar pilas de desarrollo (stacks tecnológicos) full-stack en entornos empresariales, ilustrando la inyección de dependencias en **Java** utilizando el framework **Spring Boot**.

---

## Concepto Principal (El 'Qué')

### 1. Framework vs. Biblioteca (Library)
En la ingeniería de software, la línea divisoria entre un framework y una biblioteca radica en quién tiene el control del flujo de ejecución del programa:

* **Biblioteca (Library):**
  Es una colección de funciones y clases empaquetadas que usted (el programador) invoca activamente para resolver un problema específico (ej. parsear un JSON, calcular funciones matemáticas). Su código tiene el control y decide cuándo llamar a la biblioteca.
* **Framework (Marco de Trabajo):**
  Es una estructura de arquitectura predefinida que prescribe el esqueleto de la aplicación. El framework invoca a su código en puntos de extensión específicos. Esto se conoce como el principio de **Inversión de Control (IoC - Inversion of Control)** o popularmente *"El principio de Hollywood"* (no nos llame, nosotros lo llamaremos).

### 2. Criterios de Selección de Stacks Tecnológicos
La selección de la pila de tecnologías (Base de datos, Backend, Frontend, DevOps) no debe responder a modas, sino a una evaluación ponderada de variables críticas:

1. **Arquitectura y Rendimiento:** Requerimientos de velocidad de procesamiento, concurrencia (ej. programación reactiva vs. hilos bloqueantes) y consumo de memoria.
2. **Curva de Aprendizaje y Disponibilidad de Talento:** Costo y viabilidad de capacitar al equipo de desarrollo actual o contratar programadores en el mercado local con dominio en la tecnología (ej. Java y .NET tienen mayor oferta de nivel corporativo).
3. **Ecosistema y Soporte Comunitario:** Existencia de abundante documentación, bibliotecas de terceros probadas, parches de seguridad frecuentes y respaldo de organizaciones sólidas (ej. Oracle/VMware para Spring, Microsoft para .NET, Google para Angular).
4. **Costo Total de Propiedad (TCO):** Licenciamiento de herramientas, costo operativo del hosting en la nube (ej. consumo de RAM de las JVM vs. contenedores ligeros de Node.js) y mantenimiento a largo plazo.

```
Flujo de Control:
Biblioteca:  [Su Código] ─────── Llama ───────> [Biblioteca (ej. Gson)]
Framework:   [Framework (Spring)] ─── Llama ───> [Su Componente (@Service)]
```

---

## Analogía (La Intuición)

Considere la diferencia entre construir una casa utilizando **herramientas de carpintería** vs. mudarse a una **casa prefabricada modular**:
* **La Biblioteca es una caja de herramientas (martillo, sierra, taladro):** Usted tiene el control absoluto. Usted decide cuándo tomar el martillo, dónde clavar el clavo y cómo estructurar las paredes de la casa. Si usted no usa las herramientas, no pasa nada; ellas no actúan por sí solas.
* **El Framework es una casa prefabricada con sistemas automáticos:** La estructura de la casa ya está construida (los cimientos, las tuberías, el cableado). El sistema eléctrico de la casa (el framework) tiene el control: él decide cuándo encender la calefacción o bombear agua. Usted solo interviene para colocar su propio decorado o conectar electrodomésticos en los enchufes predefinidos (los puntos de extensión del framework). Si usted intenta cambiar las tuberías de agua por los ductos de electricidad, la estructura colapsará, porque debe seguir las reglas de construcción de la casa.

## Ejemplo de Código e Implementación (El 'Cómo')

La Inversión de Control se materializa típicamente mediante el patrón de **Inyección de Dependencias (DI)**. A continuación, se presenta un caso en **Java** usando **Spring Boot**. El framework se encarga de instanciar, configurar y destruir los objetos, inyectándolos automáticamente en las clases que los requieren sin que el programador tenga que inicializarlos manualmente con el operador `new`:

```java
package cr.ac.ucr.if0009.frameworks;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.stereotype.Component;
import org.springframework.stereotype.Service;

// 1. Definición del Contrato (Interface)
interface ServicioNotificaciones {
    void enviarMensaje(String destinatario, String mensaje);
}

// 2. Implementación controlada por el Framework
@Service // Indica a Spring que instancie y administre este Bean en su contenedor IoC
class ServicioEmail implements ServicioNotificaciones {
    @Override
    public void enviarMensaje(String destinatario, String mensaje) {
        System.out.printf("Email enviado a %s: %s\n", destinatario, mensaje);
    }
}

// 3. Componente que consume el servicio vía Inyección de Dependencias
@Component
class GestorUsuarios {
    private final ServicioNotificaciones servicioNotificaciones;

    // Inyección por Constructor (Recomendada): Spring busca un Bean compatible e inyecta la instancia
    @Autowired
    public GestorUsuarios(ServicioNotificaciones servicioNotificaciones) {
        this.servicioNotificaciones = servicioNotificaciones;
    }

    public void registrarUsuario(String correo) {
        System.out.println("Registrando usuario en la base de datos...");
        // Consumir el servicio sin haber hecho jamás "new ServicioEmail()"
        servicioNotificaciones.enviarMensaje(correo, "Bienvenido al sistema UCR.");
    }
}

// 4. Clase Principal de Arranque del Framework
@SpringBootApplication
public class AplicacionDemo implements CommandLineRunner {

    private final GestorUsuarios gestorUsuarios;

    @Autowired
    public AplicacionDemo(GestorUsuarios gestorUsuarios) {
        this.gestorUsuarios = gestorUsuarios;
    }

    public static void main(String[] args) {
        // Ejecuta el framework, inicializando el contenedor de inversión de control (ApplicationContext)
        SpringApplication.run(AplicacionDemo.class, args);
    }

    @Override
    public void run(String... args) throws Exception {
        // Método invocado automáticamente por el ciclo de vida de Spring al arrancar
        gestorUsuarios.registrarUsuario("estudiante@ucr.ac.cr");
    }
}
```

### Explicación Línea por Línea
* **`@SpringBootApplication`**: Configura automáticamente el escaneo de componentes, la configuración y el arranque del servidor integrado.
* **`@Service` y `@Component`**: Son estereotipos de Spring. Le dicen al framework: *"Esta clase es de tu propiedad, instánciala al arrancar y mantenla en tu memoria (ApplicationContext)"*.
* **`@Autowired`**: Indica el punto exacto donde Spring debe resolver la dependencia. Al ver que `GestorUsuarios` requiere un `ServicioNotificaciones`, el framework busca en su memoria qué clase implementa dicha interfaz (encuentra `ServicioEmail`), crea una instancia y la inyecta en el constructor de forma transparente.
* **`CommandLineRunner` y `run(...)`**: Es un punto de enganche del ciclo de vida del framework. El programador no llama al método `run`, sino que Spring invoca este método de manera automática una vez que todo el sistema de Inyección de Dependencias ha sido cargado con éxito.

## Trampas Comunes (Gotchas)

1. **El Acoplamiento Oculto mediante el operador `new`:**
   Si usted utiliza el operador `new` dentro de un framework (ej. `private ServicioEmail servicio = new ServicioEmail();`), anula la capacidad del framework de gestionar el ciclo de vida del objeto, realizar inyecciones y aplicar aspectos de seguridad o transacciones.
   * *Solución:* Delegue siempre la instanciación de dependencias al framework utilizando `@Autowired` y constructor injection.

2. **Dependencias Circulares:**
   Ocurre cuando la Clase A requiere a la Clase B en su constructor, y a su vez la Clase B requiere a la Clase A (A -> B -> A). Al arrancar, el framework no sabrá cuál instanciar primero y abortará con una excepción de tipo `BeanCurrentlyInCreationException`.
   * *Solución:* Rediseñe sus componentes para eliminar el acoplamiento directo, rompa el ciclo extrayendo la lógica común a una tercera clase intermedia (Clase C), o use inyección vía Setter con la anotación `@Lazy` (aunque esto último es una mala práctica de diseño arquitectónico).
