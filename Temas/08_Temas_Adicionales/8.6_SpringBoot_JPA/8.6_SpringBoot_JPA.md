# Tema 8.6: Spring Boot y JPA — Persistencia Avanzada y Buenas Prácticas

## Resumen

Esta lectura conceptual aborda los temas avanzados de persistencia en Java utilizando **Spring Data JPA** e **Hibernate** en el contexto de Spring Boot. Se explican los patrones para el diseño de relaciones bidireccionales, el uso de consultas personalizadas mediante **JPQL** y **SQL Nativo**, y la implementación de la **auditoría automatizada** para el rastreo de modificaciones de registros. El objetivo es proporcionar al estudiantado las herramientas técnicas para construir modelos de persistencia robustos, eficientes y fáciles de mantener.

---

## Concepto Principal (El 'Qué')

### 1. Mapeo de Relaciones Avanzadas
El mapeo de relaciones entre tablas en una base de datos relacional debe traducirse de manera eficiente en Java. Existen dos enfoques para gestionar estas relaciones:
*   **Relación Unidireccional:** Solo una de las entidades conoce la existencia de la relación (ej. `Pelicula` tiene una referencia a `Genero`, pero `Genero` no sabe nada de `Pelicula`).
*   **Relación Bidireccional:** Ambas entidades tienen referencias mutuas en memoria. Para evitar inconsistencias, una de las partes debe definirse como la **propietaria de la relación** (usualmente la que posee la llave foránea física, como `@ManyToOne`), y la otra parte se define como la **inversa** utilizando el atributo `mappedBy`.

Al modelar relaciones `@OneToMany` (uno a muchos), es una buena práctica activar la eliminación de huérfanos (`orphanRemoval = true`), lo cual indica a Hibernate que elimine físicamente de la base de datos cualquier registro secundario que sea removido de la colección en memoria del padre.

### 2. Consultas Personalizadas: JPQL vs SQL Nativo
Spring Data JPA genera consultas automáticas basándose en el nombre de los métodos de interfaz (ej. `findByTitulo`). Sin embargo, para consultas complejas con agrupamientos o múltiples uniones (*joins*), se requiere utilizar la anotación `@Query`:
*   **JPQL (Java Persistence Query Language):** Es un lenguaje de consultas orientado a objetos que opera sobre las entidades Java y sus atributos en lugar de las tablas y columnas físicas de la base de datos. Garantiza la independencia del motor de base de datos (portabilidad).
*   **SQL Nativo:** Es la sintaxis SQL estándar específica del motor de base de datos en uso (ej. Microsoft SQL Server). Se activa configurando `nativeQuery = true` y es útil para consumir optimizaciones específicas del motor o cláusulas no soportadas por JPQL.

Cuando una consulta en el repositorio modifica datos (ej. un `UPDATE` o `DELETE` masivo), el método debe decorarse de forma obligatoria con las anotaciones `@Modifying` (indica que la consulta altera registros) y `@Transactional` (controla la transacción).

### 3. Auditoría Automática (Auditing)
En aplicaciones corporativas, es un requisito legal y de seguridad registrar el historial de auditoría de cada registro: quién lo creó, en qué fecha y quién fue el último usuario en modificarlo. Spring Data JPA automatiza este proceso a través de **Spring Data Auditing**. 

Al habilitar esta característica mediante `@EnableJpaAuditing` en una clase de configuración, el framework intercepta los eventos de persistencia (`@PrePersist` y `@PreUpdate`) y rellena automáticamente los campos correspondientes decorados con anotaciones de auditoría (ej. `@CreatedDate`, `@LastModifiedDate`).

## Analogía (La Intuición)

*   **JPA como un Gestor de Biblioteca Automatizado:** Imagine una biblioteca grande. Si usted tiene libros (entidades) y géneros literarios (categorías). Un gestor de biblioteca tradicional (JDBC) requiere que usted busque el libro en el estante, lo anote en una bitácora física, vaya a la sección de géneros a registrarlo y luego actualice el inventario manual. JPA actúa como un gestor de biblioteca con sensores RFID en cada libro: al colocar un libro en el estante de "Ciencia Ficción" (asociación en memoria), los sensores detectan el movimiento y actualizan la base de datos central de inmediato sin que usted tenga que escribir una sola línea en papel.
*   **La Auditoría como una Bitácora de Caja Fuerte:** Piense en una caja fuerte de un banco. Cada vez que alguien introduce o saca dinero, un sistema electrónico registra la huella digital del empleado y la fecha exacta en la que se abrió la compuerta. El empleado no tiene que escribir en una hoja su nombre ni la hora; el sistema de seguridad (Auditing) se encarga de estampar esa metadata de forma automática e inviolable para efectos de control.

## Ejemplo de Código e Implementación (El 'Cómo')

A continuación se muestra el diseño de una entidad base auditada, una relación bidireccional entre `Pelicula` y `Review` (reseña), consultas personalizadas en el repositorio y la activación del soporte de auditoría en la configuración de Spring Boot.

### 1. Entidad Base de Auditoría (`AuditableEntity.java`)
Cree la clase padre de persistencia en la ruta:  
`src/main/java/cr/ac/ucr/paraiso/ie/carnet/practica3/domain/AuditableEntity.java`

```java
package cr.ac.ucr.paraiso.ie.carnet.practica3.domain;

import jakarta.persistence.Column;
import jakarta.persistence.EntityListeners;
import jakarta.persistence.MappedSuperclass;
import org.springframework.data.annotation.CreatedDate;
import org.springframework.data.annotation.LastModifiedDate;
import org.springframework.data.jpa.domain.support.AuditingEntityListener;
import java.time.LocalDateTime;

@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class AuditableEntity {

    @CreatedDate
    @Column(name = "fecha_creacion", updatable = false)
    private LocalDateTime fechaCreacion;

    @LastModifiedDate
    @Column(name = "fecha_modificacion")
    private LocalDateTime fechaModificacion;

    public LocalDateTime getFechaCreacion() { return fechaCreacion; }
    public void setFechaCreacion(LocalDateTime f) { this.fechaCreacion = f; }

    public LocalDateTime getFechaModificacion() { return fechaModificacion; }
    public void setFechaModificacion(LocalDateTime f) { 
        this.fechaModificacion = f; 
    }
}
```

### 2. Clase Entidad con Relación Bidireccional (`Pelicula.java`)
Heredamos de la entidad de auditoría y definimos la relación con `Review` en:  
`src/main/java/cr/ac/ucr/paraiso/ie/carnet/practica3/domain/Pelicula.java`

```java
package cr.ac.ucr.paraiso.ie.carnet.practica3.domain;

import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.List;

@Entity
@Table(name = "Pelicula")
public class Pelicula extends AuditableEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "pelicula_id")
    private Integer id;

    @Column(nullable = false, length = 50)
    private String titulo;

    // Relación bidireccional: mappedBy apunta al atributo en Review
    @OneToMany(
        mappedBy = "pelicula", 
        cascade = CascadeType.ALL, 
        orphanRemoval = true,
        fetch = FetchType.LAZY
    )
    private List<Review> reviews = new ArrayList<>();

    public Pelicula() {}

    public Integer getId() { return id; }
    public void setId(Integer id) { this.id = id; }

    public String getTitulo() { return titulo; }
    public void setTitulo(String t) { this.titulo = t; }

    public List<Review> getReviews() { return reviews; }
    public void setReviews(List<Review> list) { this.reviews = list; }

    // Helper methods para mantener la consistencia bidireccional en memoria
    public void addReview(Review review) {
        reviews.add(review);
        review.setPelicula(this);
    }

    public void removeReview(Review review) {
        reviews.remove(review);
        review.setPelicula(null);
    }
}
```

### 3. Clase Entidad Hija (`Review.java`)
Cree la clase que representa la reseña en la ruta:  
`src/main/java/cr/ac/ucr/paraiso/ie/carnet/practica3/domain/Review.java`

```java
package cr.ac.ucr.paraiso.ie.carnet.practica3.domain;

import jakarta.persistence.*;

@Entity
@Table(name = "Review")
public class Review extends AuditableEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "review_id")
    private Integer id;

    @Column(nullable = false, length = 500)
    private String comentario;

    @Column(nullable = false)
    private int calificacion; // Escala 1 a 5

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "pelicula_id", nullable = false)
    private Pelicula pelicula;

    public Review() {}

    public Integer getId() { return id; }
    public void setId(Integer id) { this.id = id; }

    public String getComentario() { return comentario; }
    public void setComentario(String c) { this.comentario = c; }

    public int getCalificacion() { return calificacion; }
    public void setCalificacion(int c) { this.calificacion = c; }

    public Pelicula getPelicula() { return pelicula; }
    public void setPelicula(Pelicula p) { this.pelicula = p; }
}
```

### 4. Interfaz Repositorio con Consultas Avanzadas (`PeliculaRepository.java`)
Implemente las consultas JPQL y SQL Nativo en la interfaz del paquete `data`:  
`src/main/java/cr/ac/ucr/paraiso/ie/carnet/practica3/data/PeliculaRepository.java`

```java
package cr.ac.ucr.paraiso.ie.carnet.practica3.data;

import cr.ac.ucr.paraiso.ie.carnet.practica3.domain.Pelicula;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Modifying;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;
import org.springframework.stereotype.Repository;
import java.util.List;

@Repository
public interface PeliculaRepository extends JpaRepository<Pelicula, Integer> {

    // Consulta JPQL: Opera sobre entidades y atributos de Java
    @Query("SELECT p FROM Pelicula p JOIN p.reviews r WHERE r.calificacion >= :score")
    List<Pelicula> buscarPeliculasConBuenasResenas(
        @Param("score") int score
    );

    // Consulta SQL Nativa: Opera sobre las tablas físicas
    @Query(value = "SELECT * FROM Pelicula p WHERE p.titulo LIKE %:keyword%", 
           nativeQuery = true)
    List<Pelicula> buscarPorTituloNativo(
        @Param("keyword") String keyword
    );

    // Consulta de Modificación Masiva
    @Modifying
    @Query("UPDATE Pelicula p SET p.titulo = UPPER(p.titulo) WHERE p.id = :id")
    int convertirTituloAMayusculas(
        @Param("id") Integer id
    );
}
```

### Explicación del Código Línea por Línea

*   **`AuditableEntity.java` (Línea 10):** La anotación `@MappedSuperclass` indica que esta clase no se mapeará como una tabla física independiente, sino que sus campos se heredarán y agregarán a las tablas de las entidades hijas.
*   **`AuditableEntity.java` (Línea 11):** `@EntityListeners(AuditingEntityListener.class)` registra el escuchador interno de Spring Data JPA que inyecta automáticamente la hora actual antes del insert o update.
*   **`Pelicula.java` (Línea 23):** En la relación bidireccional, configuramos `mappedBy = "pelicula"`. Esto informa a Hibernate que la relación está controlada físicamente por la columna `pelicula_id` definida en la entidad `Review`, evitando que se cree una tabla intermedia redundante.
*   **`Pelicula.java` (Líneas 40-48):** Los métodos auxiliares `addReview` y `removeReview` son indispensables para mantener la consistencia del grafo de objetos en memoria de forma bidireccional.
*   **`PeliculaRepository.java` (Línea 15):** La consulta JPQL hace un `JOIN p.reviews` en base al grafo de objetos definido en Java, en lugar de declarar columnas físicas de llaves foráneas.
*   **`PeliculaRepository.java` (Línea 27):** Para operaciones `@Modifying`, es obligatorio que el método devuelva `int` o `void` indicando el número de filas alteradas por la consulta.

## Trampas Comunes

*   **Ignorar mappedBy en Relaciones Bidireccionales:**  
    Si se omiten las relaciones inversas o el atributo `mappedBy`, Hibernate asume que son relaciones independientes y creará tablas de unión innecesarias de forma automática, degradando el rendimiento.
    *   *Solución:* Especifique siempre `mappedBy` en la entidad inversa (la que no tiene la llave foránea).
*   **La Trampa del orphanRemoval sin Cascade:**  
    Configurar `orphanRemoval = true` sin definir `CascadeType.ALL` o `CascadeType.PERSIST` impedirá que Hibernate sincronice los cambios si se agregan nuevos elementos a la colección del padre.
    *   *Solución:* Combine siempre `orphanRemoval = true` con `cascade = CascadeType.ALL` para asegurar la persistencia en cascada completa.
*   **Modificaciones sin Limpiar el Contexto de Persistencia:**  
    Las consultas masivas anotadas con `@Modifying` ejecutan sentencias directas contra la base de datos, evadiendo la memoria caché de primer nivel de Hibernate (el *Persistence Context*). Esto puede provocar que llamadas posteriores recuperen datos viejos que aún residen en memoria RAM.
    *   *Solución:* Añada el parámetro `clearAutomatically = true` en la anotación `@Modifying` para limpiar la memoria caché inmediatamente tras ejecutar la consulta:
        ```java
        @Modifying(clearAutomatically = true)
        ```
