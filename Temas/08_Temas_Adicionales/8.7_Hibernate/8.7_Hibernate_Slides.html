JPA vs Hibernate: Especificación y Motor

  • JPA (Java Persistence API):
    • Es una especificación estándar (reglas y anotaciones, ej. @Entity).
    • Define la interfaz general pero no contiene código ejecutable.
  • Hibernate:
    • Es la implementación (el motor de persistencia).
    • Traduce las operaciones del estándar JPA en consultas SQL nativas del motor (ej. SQL Server, PostgreSQL) en tiempo de ejecución.
    • Proveedor por defecto en el ecosistema Spring Boot.

El Contexto de Persistencia (Caché L1)

  • ¿Qué es el Contexto de Persistencia?
    • Memoria caché a nivel de transacción (Caché de Primer Nivel).
    • Administrado por el EntityManager de JPA.
  • Funciones Clave:
    • Rastrear todos los objetos cargados durante una transacción activa.
    • Garantizar la identidad de objetos (un registro de base de datos se mapea a una única instancia en memoria RAM).
    • Evitar consultas redundantes a la base de datos dentro de la misma transacción.

Ciclo de Vida de las Entidades

  • Las entidades transicionan por cuatro estados administrados por Hibernate:
    1. Transient (Transitorio): Objeto creado con new. No tiene ID en base de datos ni asociación al context de persistencia.
    2. Persistent (Persistente / Managed): Asociado al contexto y con ID en base de datos. Los cambios en atributos se guardarán de forma automática.
    3. Detached (Desprendido): Tiene ID en base de datos, pero la sesión de persistencia está cerrada. Modificaciones no se guardan automáticamente.
    4. Removed (Eliminado): Marcado para borrado físico al finalizar la transacción.

Dirty Checking (Comprobación de Cambios)

  • Mecanismo de Detección:
    • Hibernate guarda una copia instantánea (snapshot) al cargar la entidad.
    • Al hacer commit de la transacción, compara el estado actual con el snapshot.
  • Flushing Automático:
    • Si detecta modificaciones, Hibernate genera y ejecuta los UPDATE en SQL automáticamente.
    • Regla de oro: No es necesario llamar a .save() o .update() para entidades persistentes dentro de métodos @Transactional.

El Problema de Consultas N+1 SELECT

  • ¿Por qué ocurre?
    • Cargar una lista de $N$ registros con relaciones de carga perezosa (Lazy).
    • Al iterar y leer la propiedad hija de cada registro, Hibernate realiza $N$ consultas adicionales a base de datos.
    • Total consultas: 1 consulta inicial + $N$ consultas secundarias.
  • Solución: JOIN FETCH:
    • Indica a Hibernate cargar la relación de forma anticipada mediante una sola consulta SQL combinada (JOIN) a nivel de base de datos.

Analogías del Tema

  • La Pizarra de Borrador (Contexto de Persistencia):
    • Modificar variables en la pizarra (Caché L1) no altera el archivador físico (Base de Datos). Los cambios se escriben en el papel oficial solo al presionar "Imprimir" (flushing al hacer commit).
  • El Inspector de Entrega (Dirty Checking):
    • La rentadora compara el estado actual del auto contra la foto inicial. Detecta y cobra raspones (updates) sin que usted deba notificarlos.

Código: Ciclo de Vida y Dirty Checking

@Transactional
public void demostrarCicloVida(Integer peliculaId) {
    // 1. Estado Transitorio (Transient)
    Pelicula nueva = new Pelicula();
    nueva.setTitulo("Inception");

    // 2. Estado Persistente (Managed)
    entityManager.persist(nueva);

    // 3. Dirty Checking en acción
    Pelicula existente = repository.findById(peliculaId).orElseThrow();
    existente.setTitulo("The Matrix Resurrections");
    
    // Hibernate ejecutará automáticamente el UPDATE para 'existente'
    // al finalizar el método @Transactional sin llamar a save()
}

@Transactional
public void demostrarDetached(Integer peliculaId) {
    Pelicula p = repository.findById(peliculaId).orElseThrow();

    // Desasociar del contexto de persistencia L1
    entityManager.detach(p); // Ahora está DETACHED

    p.setTitulo("Título Modificado en Memoria");
    
    // Al concluir el método, el cambio de título NO se guardará
    // en la base de datos debido a que la entidad ya no es administrada
}

Código: Solución a N+1 con JOIN FETCH

@Repository
public interface PeliculaRepository extends JpaRepository<Pelicula, Integer> {

    // JOIN FETCH: Trae películas y reviews asociadas en un único SELECT
    @Query("SELECT DISTINCT p FROM Pelicula p LEFT JOIN FETCH p.reviews")
    List<Pelicula> obtenerPeliculasConReviewsOptimizadas();
}

Trampas Comunes de Rendimiento

  • Llamar Redundadamente a .save():
    • Sobrecarga de llamadas en métodos transaccionales donde el Dirty Checking ya opera por defecto.
  • LazyInitializationException:
    • Intentar acceder a atributos LAZY fuera del servicio transaccional (entidad en estado Detached).
  • Agotamiento de Memoria en Cargas Masivas:
    • Guardar miles de objetos llena la Caché L1 y ralentiza el Dirty Checking.
    • Solución: Usar procesos por lotes llamando periódicamente a flush() y clear().
