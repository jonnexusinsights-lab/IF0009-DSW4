# Algoritmo Token Bucket

* **Mecánica:**
  * Un contenedor acumula tokens a una tasa constante $R$ por segundo.
  * Capacidad máxima $B$ (permite ráfagas de consumo repentinas).
  * Cada petición consume 1 token.
* Si el balde tiene tokens disponibles $\implies$ Petición procesada (**200 OK**).
* Si el balde está vacío $\implies$ Petición bloqueada inmediatamente (**429 Too Many Requests**).

---

# Estándar HTTP 429 y Cabeceras

* Cuando un cliente excede su límite, la API responde:
  * **Status:** `429 Too Many Requests`.
  * **`Retry-After: 60`** (segundos requeridos antes de volver a intentar).
  * **`X-RateLimit-Remaining: 0`** (tokens restantes en la ventana actual).
* Permite que clientes móviles (Flutter) pausen peticiones de forma ordenada.

# Filtro Defensivo en Java 25 (Bucket4j)

```java
@Component
public class RateLimitFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest req, 
            HttpServletResponse res, FilterChain chain) 
            throws ServletException, IOException {
        
        Bucket bucket = obtenerBucketPorIp(req);
        if (bucket.tryConsume(1)) {
            chain.doFilter(req, res);
        } else {
            res.setStatus(429);
            res.setHeader("Retry-After", "60");
            res.getWriter().write("{\"error\": \"Límite de tasa excedido.\"}");
        }
    }
}
```

* Intercepta el tráfico antes de consumir recursos en la base de datos.

# Trampa Crítica: La IP detrás de Balanceadores

* En producción, la aplicación reside detrás de un Proxy o Ingress (Nginx, ALB).
* Si utiliza `request.getRemoteAddr()`, obtendrá la IP interna del balanceador.
  * *¡Bloqueará a todos los clientes del mundo si uno solo excede el límite!*
* **Solución Obligatoria:**
  * Inspeccionar la cabecera `X-Forwarded-For: cliente_ip, proxy_ip`.
