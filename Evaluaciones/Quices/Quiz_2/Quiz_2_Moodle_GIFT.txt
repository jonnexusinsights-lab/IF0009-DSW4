// Pregunta 1: Ciclo de Vida de Entidades JPA/Hibernate y Dirty Checking
// ------------------------------------------------------------------------------
::Q1_JPA_Dirty_Checking:: [html]Un desarrollador ejecuta un método anotado con <code>@Transactional</code> en la capa de servicio para actualizar el precio de un producto en el sistema. Dentro del método, busca la entidad por ID mediante <code>productoRepository.findById(id)</code>, ejecuta la modificación mediante el método modificador <code>producto.setPrecio(nuevoPrecio)</code> y <b>NO</b> invoca explícitamente el método <code>productoRepository.save(producto)</code>. Sin embargo, al concluir la ejecución de la transacción, la base de datos ejecuta automáticamente la instrucción SQL <code>UPDATE</code>.<br/><br/>¿Cuál es el mecanismo interno de Hibernate que produce esta sincronización implícita y en qué estado se encuentra la entidad durante la transacción? {
	~La entidad se encuentra en estado <i>Transient</i> y Spring Data JPA dispara un evento asíncrono que recrea la tabla en la base de datos mediante sentencias DDL. #Incorrecto. El estado Transient corresponde a objetos instanciados con new sin identificador ni contexto de persistencia.
	=La entidad se encuentra en estado <i>Persistent</i> (asociada al Contexto de Persistencia), por lo que Hibernate realiza <i>Dirty Checking</i> al ejecutar el <i>flush</i> automático y sincroniza los cambios en la base de datos sin requerir save(). #¡Correcto! Al estar en estado Persistent, Hibernate realiza Dirty Checking durante el flush automático de la transacción e invalida el estado emitiendo la sentencia SQL UPDATE.
	~La entidad se encuentra en estado <i>Detached</i> y el repositorio activa una captura de excepciones de base de datos que reintenta la modificación mediante disparadores (<i>triggers</i>) SQL. #Incorrecto. Las entidades en estado Detached requieren una llamada explícita a merge() para reconectarse a la sesión.
	~El comportamiento se debe a un error de compilación de Hibernate; las entidades en JPA nunca pueden sincronizarse con la base de datos a menos que se anote la clase con <code>@DynamicUpdate</code>. #Incorrecto. Dirty Checking es una característica central de JPA/Hibernate y no exige @DynamicUpdate para operar.
}

// Pregunta 2: Diagnóstico de Rendimiento ORM: El Problema N+1 SELECT
// ------------------------------------------------------------------------------
::Q2_N_Plus_1_JOIN_FETCH:: [html]En una API REST de logística y envíos, un endpoint <code>@GetMapping("/api/v1/empresas")</code> retorna una lista de 50 empresas de transporte. Cada entidad <code>EmpresaLogistica</code> mantiene una relación <code>@OneToMany</code> mapeada hacia su colección de <code>Vehiculo</code> con la estrategia por defecto (<code>FetchType.LAZY</code>). Al consultar la lista completa de empresas junto con sus vehículos asociados para la respuesta JSON, las herramientas de perfilado muestran que Hibernate ejecuta <b>51 consultas SQL <code>SELECT</code> independientes</b> para atender una sola petición HTTP.<br/><br/>¿Cómo se denomina esta falla de rendimiento en mapeadores relacionales y cuál es la solución técnica más eficiente mediante Spring Data JPA? {
	~Se denomina <i>Heap Overflow Failure</i> y se soluciona cambiando la anotación de la relación a <code>@OneToOne(fetch = FetchType.EAGER)</code>. #Incorrecto. Modificar a @OneToOne altera la cardinalidad del modelo de dominio y no soluciona el patrón de carga.
	=Se denomina <i>Problema N+1 SELECT</i> y se soluciona definiendo una consulta JPQL con <code>JOIN FETCH</code> (ej. <code>@Query("SELECT e FROM EmpresaLogistica e JOIN FETCH e.vehiculos")</code>) para recuperar las empresas y sus colecciones en una única consulta SQL. #¡Correcto! El problema N+1 SELECT genera 1 consulta principal y N secundarias. Se resuelve mediante JOIN FETCH en JPQL para traer los datos en un solo round-trip.
	~Se denomina <i>Deadlock de Persistencia</i> y se resuelve eliminando la anotación <code>@Entity</code> e instanciando un controlador nativo JDBC con cursores en memoria. #Incorrecto. No se trata de un bloqueo de concurrencia (Deadlock) ni exige abandonar JPA.
	~Se denomina <i>Circular Dependency Defect</i> y se remedia agregando la directiva <code>@JsonIgnoreProperties</code> en la interfaz del repositorio de datos. #Incorrecto. @JsonIgnoreProperties evita bucles infinitos en serialización Jackson, pero no resuelve la ejecución de consultas SQL secundarias.
}

// Pregunta 3: Ejercicio de Rastreo de Código: Intercepción Global de Errores (@RestControllerAdvice)
// ------------------------------------------------------------------------------
::Q3_RestControllerAdvice_Protocol_Mismatch:: [html]Analice la siguiente implementación de un manejador centralizado de excepciones en Spring Boot:<br/><br/><pre><code>@RestControllerAdvice<br/>public class GlobalExceptionHandler \{<br/><br/>    @ExceptionHandler(RecursoNoEncontradoException.class)<br/>    public ResponseEntity&lt;Map&lt;String, Object&gt;&gt; manejarNoEncontrado(<br/>            RecursoNoEncontradoException ex) \{<br/>        <br/>        Map&lt;String, Object&gt; error \= new HashMap&lt;&gt;();<br/>        error.put("timestamp", LocalDateTime.now());<br/>        error.put("status", 404);<br/>        error.put("error", "Not Found");<br/>        error.put("message", ex.getMessage());<br/>        <br/>        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(error);<br/>    \}<br/>\}</code></pre><br/>Suponga que un cliente realiza una consulta HTTP a un endpoint inexistente y el servicio lanza <code>throw new RecursoNoEncontradoException("El vehículo con placa ABC-123 no existe")</code>.<br/><br/>¿Qué inconsistencia de protocolo ocurre en la respuesta entregada al cliente HTTP al ejecutar este código? {
	=El cliente recibe una cabecera con código de estado <code>HTTP 400 Bad Request</code>, a pesar de que el cuerpo JSON interno indica <code>"status": 404</code>, debido a que <code>ResponseEntity.status(...)</code> fija el código HTTP final del paquete. #¡Correcto! ResponseEntity.status(...) define la cabecera real HTTP de la red (HTTP 400), creando una discrepancia de protocolo contra el cuerpo JSON (404).
	~El cliente recibe un código <code>HTTP status 500 Internal Server Error</code> porque las excepciones personalizadas no permiten el retorno de colecciones <code>Map</code>. #Incorrecto. Spring Boot serializa mapas Java a JSON mediante la librería Jackson sin problemas.
	~El cliente recibe una respuesta exitosa <code>HTTP status 200 OK</code> con un cuerpo vacío debido a la falta de la anotación <code>@ResponseBody</code>. #Incorrecto. @RestControllerAdvice incluye sintácticamente @ResponseBody implícito para todos sus métodos.
	~El código genera una excepción de compilación <code>TypeMismatchException</code> en Spring Boot porque <code>@ExceptionHandler</code> solo admite tipos primitivos. #Incorrecto. @ExceptionHandler acepta cualquier tipo de excepción personalizada que derive de Throwable.
}

// Pregunta 4: Ejercicio de Rastreo de Código: Evaluación de Control de Acceso (Spring Security & RBAC)
// ------------------------------------------------------------------------------
::Q4_Spring_Security_RBAC_Authorization:: [html]Examine la siguiente configuración de la cadena de filtros de seguridad en un sistema Spring Boot 3:<br/><br/><pre><code>@Bean<br/>public SecurityFilterChain filterChain(HttpSecurity http) <br/>        throws Exception \{<br/>    http<br/>        .csrf(csrf -&gt; csrf.disable())<br/>        .authorizeHttpRequests(auth -&gt; auth<br/>            .requestMatchers("/api/v1/auth/**").permitAll()<br/>            .requestMatchers(HttpMethod.GET, "/api/v1/envios/**")<br/>                .hasAnyRole("CONDUCTOR", "ADMIN")<br/>            .requestMatchers(HttpMethod.POST, "/api/v1/envios/**")<br/>                .hasRole("ADMIN")<br/>            .anyRequest().authenticated()<br/>        )<br/>        .sessionManagement(sess -&gt; sess<br/>            .sessionCreationPolicy(SessionCreationPolicy.STATELESS)<br/>        );<br/>    return http.build();<br/>\}</code></pre><br/>Un usuario autenticado cuyos datos en el token JWT otorgan la autoridad <code>ROLE_CONDUCTOR</code> intenta enviar la siguiente solicitud HTTP a la API REST:<br/><br/><code>POST /api/v1/envios/</code> con el cuerpo JSON de un nuevo paquete.<br/><br/>¿Cuál es el resultado exacto generado por el módulo de seguridad ante esta solicitud? {
	~La solicitud se procesa con éxito retornando <code>201 Created</code>, ya que la directiva <code>permitAll()</code> al inicio del bloque anula los controles posteriores. #Incorrecto. permitAll() sólo aplica para las rutas autorizadas expresamente bajo /api/v1/auth/**.
	=La capa de seguridad deniega el acceso y retorna el código de estado <code>HTTP status 403 Forbidden</code>, debido a que el rol <code>ROLE_CONDUCTOR</code> no cuenta con la autoridad <code>ROLE_ADMIN</code> exigida para el verbo <code>POST</code> en esa ruta. #¡Correcto! Al no tener el rol ROLE_ADMIN requerido para POST, Spring Security rechaza el acceso devolviendo HTTP 403 Forbidden.
	~La solicitud redirige automáticamente al usuario a una página HTML de inicio de sesión con el código <code>HTTP 302 Found</code>. #Incorrecto. En arquitecturas stateless REST no se utilizan redirecciones 302 a formularios HTML de login.
	~Spring Security genera una excepción runtime <code>ExpiredJwtException</code> y reinicia el contenedor embebido Tomcat. #Incorrecto. Faltas de autorización deniegan el acceso con 403 y no reinician los servidores web.
}

// Pregunta 5: Seguridad JWT: Anatomía y Mecanismo de Revocado (RFC 7519)
// ------------------------------------------------------------------------------
::Q5_JWT_Revocation_Blacklist:: [html]Una empresa implementa autenticación mediante JSON Web Tokens (JWT) con arquitectura <i>stateless</i>. Durante una prueba de penetración, el equipo de ciberseguridad descubre que si un cliente realiza un cierre de sesión (<i>logout</i>) en la interfaz web eliminando el token de su almacenamiento local (<code>localStorage</code>), una cadena JWT interceptada previamente por un tercero continúa siendo aceptada como válida por los endpoints del back-end hasta que se cumpla su tiempo de expiración (<code>exp</code>).<br/><br/>¿A qué característica del estándar JWT se debe este comportamiento y cuál es la solución técnica recomendada para permitir la invalidación inmediata de tokens? {
	~Ocurre porque los JWTs no soportan firma digital. Se soluciona cambiando la codificación de Base64URL a XML estático. #Incorrecto. Los JWTs se firman digitalmente; la falta de revocado automático responde a su diseño stateless autocontenido.
	=Ocurre porque los JWTs son tokens autosuficientes de estado cliente (<i>stateless</i>) y el servidor no guarda sesión. Se resuelve implementando una lista de revocado (<i>Token Blacklist / Denylist</i>) que registre los identificadores <code>jti</code> invalidados y los verifique en el filtro <code>JwtAuthenticationFilter</code>. #¡Correcto! Al ser tokens sin estado, la única forma de revocación inmediata previa a la expiración es mantener una lista negra (Blacklist) de jti.
	~Ocurre porque se omitió la anotación <code>@CrossOrigin</code> en el controlador de autenticación. Se soluciona activando las cookies de sesión tradicionales <code>JSESSIONID</code>. #Incorrecto. @CrossOrigin gestiona CORS en navegadores y no tiene relación con la validez de los tokens JWT.
	~Ocurre porque la clave secreta HMAC-SHA256 ha caducado en el servidor. Se soluciona reiniciando la aplicación Spring Boot. #Incorrecto. Reiniciar el servidor no invalida firmas JWT que compartan la misma clave secreta.
}
